# Проект: Antibot — детекция скраперов по cookie_id

## Что делаем

Бинарная классификация cookie_id по событиям Авито за суточное окно.
target = 1 — кука известного сервиса автосбора данных.
target = 0 — трафик, отнесённый к человеческому.

Для каждой cookie_id из test.csv надо вернуть score от 0 до 1.
Чем выше — тем вероятнее бот.

## Метрика

**Precision при Recall ≥ 70%.**
Cреди всех порогов, при которых модель ловит минимум 70% ботов,
берётся тот, где Precision максимален.
Порог перебирает проверяющая система, отправлять его не надо.

Одинаковые score обрабатываются группой: либо все куки с таким значением
уходят в положительные, либо ни одна. Это влияет на локальный расчёт метрики.

Диагностически показывают PR-AUC и ROC-AUC, но скор считается только по P@R≥0.7.

## Правила и ограничения

- LLM > 1B параметров и внешние API — запрещены.
- Ручная разметка теста, хардкод под cookie_id — запрещены.
- Всего **7 попыток** отправки на весь конкурс. Экономить.
- Признаки должны быть доступны на момент window_end_ts. Никакого будущего.
- Random seed = 42 везде. requirements.txt с точными версиями. Python версия в README.

## Формат сабмита

```

```

Ровно по одной строке на каждую cookie_id из test.csv.
Без пропусков, дублей, лишних cookie. Порядок как в sample_submission.csv.

# План работы в ноутбуке

Ноутбук будет одной цельной pipeline, ячейка за ячейкой:

1. **Импорты и конфиг** — SEED, пути, константы.
2. **Загрузка train/test/events** — polars если большой events, иначе pandas.
3. **Функция precision_at_recall_with_ties** — своя реализация метрики с корректной
   обработкой групп равных score. Это единственный источник правды.
4. **Функция build_features(meta, events)** — фильтрует события по окну каждой строки
   и считает агрегаты. Одна функция для train и test — гарантия отсутствия рассинхрона.
5. **EDA** — распределения target, длины окон, платформ, доля пропусков.
6. **Baseline** — LightGBM на 30 базовых фичах, time-based hold-out.
7. **Полный FE** — расширенный набор фич по группам (см. ниже).
8. **CV с корректной валидацией** — StratifiedGroupKFold + time hold-out.
9. **Обучение финальной модели** — LGBM + возможный rule-based booster.
10. **Инференс на test** — сборка submission.csv.
11. **Проверки формата сабмита** — assert'ы на дубли, пропуски, порядок.

# Валидация

- Основной сплит — **time-based hold-out**: последние ~20% окон по window_start_ts.
- Внутри train — **StratifiedGroupKFold по cookie_id**, страта по target (+ по бакету дня, если позволяет объём).
- Никакого случайного KFold — утечка через похожие окна.
- Метрика на каждом фолде — **P@R≥0.7 с обработкой ties**, среднее ± std.
- AUC/PR-AUC — только для диагностики.
- **Adversarial validation** train vs test по meta-фичам (длина окна, возраст куки, час старта) — чтобы поймать сдвиг распределений.

# Группы признаков (с гипотезами)

Все считаются в окне [window_start_ts, window_end_ts].

**Объёмные:**
- Число событий; уникальные item_id, item_category, item_location, search_query.
- Число сессий (разрыв между событиями > 30 мин).
- Счётчики по event_name и по eid; доли каждого типа.
- Нормировка на длительность окна: события в час.

**Временные ритмы (главный сигнал против ботов):**
- Медиана, std, min межсобытийных интервалов.
- Доля интервалов < 1 сек. Доля идеально равных интервалов.
- Энтропия распределения событий по часам суток — у людей провал ночью.
- Длиннейшая пауза; доля активных часов из 24.

**Воронка событий:**
- Ratio contact_action / item_view — у сборщиков контактов ≈ 1.
- Ratio photo_swipe / item_view — скраперу фото не нужны.
- Порядок: поиск → выдача → карточка → фото → контакт.
- Наличие / отсутствие login-события, показов капчи.

**Разнообразие и энтропия:**
- Энтропии по item_category, item_location, seller_type.
- Доля повторных просмотров одного item_id.
- Концентрация в одной категории / локации.

**Навигация:**
- Max search_page, доля страниц > 5 (скрапер листает глубже).
- Число уникальных search_query, средняя длина, повторы.
- Ratio (страниц выдачи) / (карточек открыто).

**Технические:**
- Согласованность platform ↔ user_agent.
- Смена user_agent внутри одной cookie в окне (человек так не делает).
- Частотность UA в популяции (редкий UA подозрительнее).
- Флаги headless / старых версий (парсим через ua-parser или user-agents).

**Pointer (важное против ботов):**
- Доля событий с непустыми pointer_x/y.
- std и энтропия координат; число уникальных точек.
- Признак «координаты на сетке» — повторяющиеся значения, малое число уникальных.
- Средняя скорость перемещения между последовательными точками.

**Meta (из train/test.csv):**
- Возраст куки на момент window_end_ts.
- Длительность окна.
- Час и день недели старта окна.

⚠ Meta-фичи опасны — легко выучить «в тесте окна длиннее». Проверять adversarial validation'ом.

# Специфика метрики P@R≥0.7

Метрика оценивает **только верх ранжирования**. Из этого:

- Калибровка score в [0,1] для скора **не нужна** — монотонное преобразование
  не меняет ранжирование. Формально приводим к [0,1] через мин-макс просто для формата.
- AUC — плохой прокси. PR-AUC чуть лучше. Оптимизировать надо
  верх ранжирования → тренироваться и подбирать по P@R локально.
- **Ties опасны**: если много cookie получают одинаковый score, они уходят
  группой через порог. Добавить tiebreaker (например, ε × вспомогательный score
  или одну сильную фичу) чтобы избежать плато.
- Rule-based hard flags как отдельный блок фич + возможный ручной boost
  score для явных ботов работает хорошо: метрика буквально просит найти
  «самых явных» ботов.

# Стратегия 7 попыток

1. **Sanity submission** — константа 0.5 или число событий. Проверить формат,
   установить связь локальный P@R vs LB P@R.
2. **LGBM baseline** на 30 базовых фичах.
3. **Полный FE + time-based CV** — основная рабочая модель.
4. **+ Rule-based hard flags**, доработка фич.
5. **Ансамбль / LambdaRank / focal loss** — что показало лучший CV.
6. **Финальный тюн, tiebreaker.**
7. **Резерв** — не трогать до последнего дня.

Между попытками — только локальная валидация. Если локально не выросло — не грузим.
